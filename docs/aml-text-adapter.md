# AML 文本记忆接入：方案与设计

Memoria 服务端提供 AML Add/Search 适配模块。部署 Memoria 和原有 MatrixOne 等依赖即可，不需要额外的 FastAPI/SQLite 服务。适配器只返回记忆证据；AML 平台负责回答与评分。

本文是本项目方案与设计决策的统一维护入口。后续决策直接更新对应章节，使正文始终描述当前有效方案；不追加讨论纪要、尝试过程或已被替代的方案。实现状态与目标设计分别标注，规划中的能力不能作为已完成功能交付。

### 相邻消息补全的归因与职责

当前观测到的问题属于**AML 原始对话来源接入方案的上下文能力缺口**。现有证据能确认部分答案消息没有被返回，尚不能认定 Memoria 原有业务违反了其功能契约，也未发现这些样例的消息丢失或 AML 字段转换错误。

AML Add 在 `routes/aml.rs::AddRequest::prepare` 中把每条消息分别转换为一条来源 Memory；长消息进一步分块。`ingest_source_batch` 保留原文并独立生成 embedding、持久化，另行排队做实体索引，不执行 `observe_turn` 的记忆事实抽取。默认关闭补全时，AML Search 使用 `retrieve_with_options_on_branch` 的原有图／向量／全文相关性检索；启用后在通用服务中追加来源上下文选择阶段。语义图关系扩展与来源顺序补全是不同能力。

这种组合会使“这些花是什么品种？”与“它们叫 Peruvian Lilies”成为两条分别评分的记录。回答中的代词依赖前文，而花名可能缺少问题中的人物、花卉等词项；检索命中提问并不保证返回下一条回答。长消息内部的 150 字符重叠仅连接同一条消息的分块，无法补齐两条不同消息之间的上下文。

Memoria 原有 `observe_turn_on_branch` 在配置 LLM 时可基于输入消息抽取结构化记忆，失败或未配置时也有原文回退路径。它与当前 AML 来源导入路径不同；抽取有机会把上下文表达成独立事实，但不能据此假定它必然解决这些样例，也不能把当前原始消息评测等同于对原有观察／抽取能力的完整验收。来源保真仍需保留，不能用抽取结果覆盖全部原文。

| 层 | 当前情况 | 目标职责 |
|---|---|---|
| Memoria 内的 AML Add 适配 | 保存原标识／索引及通用 `SourcePosition`；跨批次顺序尚不完整 | 将官方输入映射为通用来源结构，保留可确定的顺序和边界；不解析 opaque request_id 猜测顺序 |
| Memoria 来源存储与检索服务 | 批次内链接构建、原子保存及可选补全已实现并部署 | 按用户和分支范围批量读取邻接记录、去重并限制证据预算 |
| AML Search 适配 | 从启动配置选择来源上下文策略并封装结果，默认关闭 | 对照验证后确定正式配置，继续遵守 Top K 和官方响应格式 |
| 本地评测客户端 | 模拟官方输入并独立评分 | 评测补全收益，不在客户端读取 gold 或额外拼接数据库来源来替代服务端 Search |

**设计决策**：相邻消息补全作为来源证据检索的可配置能力，先用于 AML 来源路径的对照实验；普通事实记忆的默认检索行为保持现有语义。适配层提供通用来源位置，服务构建邻接链接并完成补全，存储层执行有界读；数据库邻接与排序逻辑不放在 HTTP handler。批次内版本已实现、部署并完成实际数据库读取检查；质量收益以固定开发对照为准。

### 邻接候选定位与相关性判定

邻接表示来源中的顺序关系，相关表示对当前问题或命中消息的解释价值。二者分别处理：来源顺序用于产生有限候选，上下文与问题用于选择返回证据；位置接近不证明语义相关，也不证明消息内容为真。

**已实现版本限定在顺序已知的单个 Add 批次内**。AML Add 在既有 metadata 中增加通用 `memoria_source_position`：内部批次键 `batch_id`、批次内 `message_index`、消息内 `chunk_index`。批次键是完整隔离请求组合的哈希，整体作为标识使用，不解析其文本。位置来自 `messages` 数组和实际分块，不来自时间戳、memory ID 排序或 LoCoMo Dialogue ID。

`source_context::attach_source_context` 在来源写入服务中根据整个批次的位置构建版本化 `memoria_source_context` 链接。每条记录最多保存 40 个相邻记录 ID 及其消息／分块位置，覆盖同一消息的邻近分块和前后 2 条消息；每个消息最多贡献 8 个分块。当前消息的分块窗口围绕命中位置，前面的消息取尾部最多 8 块，后面的消息取开头最多 8 块；完整长消息仍全部存储，补全可能只覆盖部分分块。位置、链接、来源记录及幂等凭据在既有事务中一并提交，无新增表或迁移。

Search 取原检索前 N 个命中作为锚点（默认 N=5，只有带有效来源位置与链接的记录扩展）。按配置半径过滤持久化链接，并按锚点优先级、消息距离、消息／分块位置和 ID 确定候选顺序。已在原检索结果中的邻居可直接复用，其余候选一次按主键批量读取；最多 256 个候选 ID，不按 JSON 范围全表扫描、不逐条查库。读取 SQL 约束用户、目标分支表、active 状态及来源标记；表名校验支持当前路由数据库的完整限定名，只允许剥离当前 store 的确切数据库前缀，再校验物理表名，拒绝其他数据库前缀与非法标识符。服务再校验会话、批次、消息／分块位置、未被替代状态、原有 subject/type/session 过滤及初始置信度下限 0.05。补全读取失败时记录警告并返回原检索结果；上线验收必须检查实际新增来源与回退日志，不能只看 HTTP 200。

可选择 ±1 或 ±2 条消息；±2 已完成首轮开发对照，±1 尚未评测，当前参数不是已确认的最优值。同一用户、同一会话不足以证明跨 Add 的相邻关系；不同批次的 `message_index` 会重置。实现会在批次边界停止。跨批次补全只有在有可靠来源顺序信息时扩展；内部接收序号最多证明接收先后，不能在乱序或并发输入时直接作为来源顺序。未知顺序不得由相同 timestamp 或字符串排序补造，也不增加官方未声明的必填参数。

相关性选择采用以下证据分层：

| 信号 | 用途与边界 |
|---|---|
| 已知消息／分块顺序、同来源范围 | 确定邻接候选，限制查找范围；不直接证明话题连续 |
| 已召回锚点与问题的相关性 | 为上下文窗口提供检索依据；仅围绕优先锚点扩展，不为全部 Top 100 无差别添加窗口 |
| 窗口内问答、代词解释、实体或话题延续 | 判断邻居是否解释锚点、补充所问事实；角色交替和“它／这个”等措辞仅为辅助信号 |
| 问题与组合窗口的相关性 | 比较包含锚点及邻居的证据组，而非仅比较短答复与问题的独立相似度；避免有用的代词答复再次被单条低分过滤 |
| 明显话题切换、主体不一致、重复与预算消耗 | 降低或排除无关扩展；无法判断时保留不确定性，不将推测写成新的事实 |

当前实现采用小窗口、锚点优先、距离优先的确定性补全作为实验基线，没有额外语义评分、问答关系分类或话题切换检测。上表的语义信号属于后续判别方向，不能称为已实现能力。若噪声影响答案，再独立对照窗口整体的 embedding 或 rerank；这些评分也不是相关性的真值，不因该设计预先要求新增 rerank 模型。补全用于组织检索证据，不推断事实真实性、不代替原有远距离多跳召回，也不修改原始来源文字。

选择阶段先保留原结果前 N 条，再按候选顺序选择最多 M 条上下文（默认 M=20，包含原结果中被提前组织为上下文的记录），最后按原检索顺序填充剩余名额。全部记录按 memory ID 去重，共同占用 Top K；正文 Unicode 字符总数不超过本次无补全结果的字符总数，因此某些长候选会被跳过，最终条数可能少于 Top K。保护前 N 条指保留其记录，不保证它们仍占据输出前 N 位：最终窗口内按来源顺序输出，前文可位于锚点之前。字符预算相对于同次请求的基础检索，不能保证等于历史运行的证据长度；它不是模型 token 数或官方 Search 长度规范。

展示按所属锚点优先级组织，各选定窗口内保留消息／分块来源顺序；原始 ID、角色、正文和来源时间不改写，不把整个会话打包成一条结果。邻居已有真实检索分数时保留，新增邻居没有独立检索分数时返回 `score` 缺省，不复制锚点分数或更改置信度。通用 Explain 增加原始结果数、来源上下文候选数、实际新增数、被挤出原候选数、选定上下文数、耗时及降级标志；Verbose/Analyze 另记录各上下文的锚点与消息距离。基础候选评分仅列保留的原候选，不为新增上下文伪造向量／关键词分数。AML 响应不增加专用调试字段。

## 时间语义与处理决策

### 时间定义

AML 官方将 `messages[].timestamp` 定义为可选的来源时间，单位为 Unix 毫秒；来源有时间时提供，分块不改变原值或消息顺序。它没有规定 Memoria 内部 `observed_at` 的含义，也没有要求按来源时间进行置信度衰减。官方契约不保证所有数据集都提供单条消息的精确发送时间。

| 时间 | 含义 | 处理方式 |
|---|---|---|
| AML `timestamp` | 来源消息的时间参照；具体精度取决于来源数据 | 原样保留在 metadata，转换为可读时间随证据正文返回；缺失保持未知 |
| Memoria `observed_at` | 当前 AML 来源路径初次接收证据的时间，也是现有核心衰减计算使用的起点 | 当前使用接收时间，不复制历史来源时间；成功请求重放不刷新 |
| Memoria `created_at` | 初次创建记录的时间 | 当前 AML 初次写入与 `observed_at` 一致 |
| 事件发生时间 | 正文描述的事件何时发生 | 目标能力：结合正文和来源时间推断，保留依据与不确定性；不能直接等同于 `timestamp` |
| 状态有效期／最后确认时间 | 某项状态在哪个时期成立、何时被明确确认 | 目标能力：用于状态更新与冲突处理，不能由本次导入时间代替 |

例如，来源会话发生于 2023-05-08，消息为“昨天参加了音乐会”：来源时间为 5 月 8 日，事件日期可推断为 5 月 7 日；今天导入这份记录不意味着音乐会今天发生，也不意味着历史状态今天得到重新确认。

### 当前实现

来源消息时间在正文前缀和 metadata 中保留，可随 Search 证据供 Answer 使用。`observed_at` 使用接收时间，避免新导入的历史消息立即被衰减过滤。普通 Memoria 写入和核心衰减公式保持现状。

来源写入服务为记录设置通用内部标记 `extra_metadata.memoria_record_kind = "source_evidence"`。该标记表达来源记录的处理策略，独立于 AML 或数据集名称；没有新增 Memory 类型、数据库列或 AML 请求字段。

| 位置 | 已实现策略 |
|---|---|
| 核心 `Memory::effective_confidence` | 标记的来源记录保留其初始置信度，不按年龄衰减；普通记录沿用原有公式 |
| 混合检索 | 来源记录不获接收时间的近期加分，置信度不随年龄衰减；向量、关键词及反馈仍参与排序 |
| 图检索 | 按候选 memory ID 和用户范围批量读取主记录的来源标记；直接关联来源记录的图节点不按年龄衰减置信度或排序分数 |
| 全文回退 | 来源记录不按年龄过滤，与其他来源检索路径的年龄策略一致；普通记录沿用现有行为 |
| 内置治理 | 来源记录不参加低置信度衰减删除、语义冗余删除、工具结果年龄清理和工作记忆年龄归档 |

来源记录的初始置信度仍是排序信号，混合检索原有的低置信度阈值仍存在；不按年龄衰减不代表所有低质量内容都必须返回。明确删除、撤销、隐私策略以及独立保留期限仍然有效。派生场景／摘要节点不会自动继承来源标记，自定义治理插件仍需遵守来源策略。

图检索的策略查询每批最多 256 个 memory ID，直接使用主记录作为策略依据，不维护额外的图标记副本。查询失败会按现有服务流程降级检索。当前小集诊断未产生图候选，尚不能测量该新增查询在有图候选时的时延影响。

此前写入但未带来源标记的记录没有自动迁移；验证新策略及时间映射应使用新的 run/user 范围。重放已有成功 Add 不会补写标记、改写时间或重新生成 embedding。当前本地 Docker API 镜像已包含排序、来源年龄策略及时间说明优化。

当前尚未实现事件时间抽取、按问题时间范围的结构化排序和状态有效期判断。时间文本随正文参与检索，不等于已具备完整时间推理能力。

### 设计原则：分别处理可信度、时间相关性和保留期限

1. **历史来源证据**：不因来源年代久远就降低其作为历史记录的可信度，或仅因年龄将其过滤、删除。来源可信度与正文断言的真实性分别处理；保存一条消息不能证明消息中的所有陈述都正确。
2. **当前状态**：通过明确的新陈述、纠正、冲突和有效期判断适用性。新状态可以替代旧状态在“当前状态”查询中的地位，同时保留旧来源用于历史查询；不能仅因两条消息时间不同就认定存在状态更新。
3. **时间相关性**：历史查询匹配问题关注的时期；“当前／最新”查询结合状态有效性排序。导入时间不用于判断历史事件先后。
4. **保留期限**：依据独立的数据保留策略清理。来源证据不按年龄降低可信度，不代表永久保存；AML 评测数据仍遵循官方删除要求。
5. **一致性**：混合、全文回退、图检索和治理使用一致的来源策略，避免某一路径过滤、另一路径又返回同一记录。

来源记录的年龄策略已实现。按问题时间范围排序、状态有效期判断和完整保留期限清理仍待实现；普通记忆在各检索路径中的原有年龄规则没有统一重构。

### 来源时间的使用边界

- 内部明确区分来源时间和推断的事件时间，先统一时间访问方式及来源类别，再决定是否需要新增专用数据库列。
- 不按服务器运行评测的日期推断数据集中的“现在”；时间参照来自问题、来源上下文或明确的业务时钟。无法确定时保留未知。
- 不能用消息时间直接硬过滤事件查询：2024 年的消息也可能讲述 2023 年发生的事件。时间增强先作为召回、排序和证据上下文的信号，限制条件必须有明确语义。
- 同一来源时间下仍保留消息顺序、消息与分块关联，供上下文补全使用。`request_id` 整体视为不透明字符串，不解析其中的 run/会话/分块名称推断时间或顺序。
- 内部来源说明不增加 AML 必填请求字段；不要求官方传入未声明的 metadata。

### 本地 LoCoMo 时间转换

`aml-local-client` 使用来源的 `session_*_date_time`，并将同一个会话时间赋给会话中的所有消息。它是会话级时间，不是逐条消息的精确发送时间。原会话日期、说话者及 Dialogue ID 已在正文中保留。

来源日期未指定时区，当前转换假设 UTC，在 manifest 和证据正文中明确记录。正文同时注明时间精度为会话级，单条消息时间未知，避免下游把它当成已知的精确时刻。正式 AML 输入按其实际提供的时间处理，不能据本地转换推断官方冻结 Adapter 的实现。已有本地运行产物不会重写，使用新的 prepare 结果才能获得这些说明。

## Add

```json
{
  "request_id": "eval:run-1:locomo:conv-0:chunk-0",
  "user_id": "eval:run-1:locomo:conv-0",
  "session_id": "eval:run-1:session-0",
  "messages": [
    {"role": "user", "content": "I visited Cedar Observatory.", "timestamp": 1704067200000},
    {"role": "assistant", "content": "You mentioned its violet telescope."}
  ]
}
```

三个标识和消息由调用方提供。标识、消息正文不能为空；角色限于 `user`、`assistant`。可选时间为 Unix 毫秒，支持 UTC 公元 1000—9999 年。消息顺序、角色、时间和原文片段保留在记忆中。长消息按 1000 个 Unicode 字符分块，重叠 150 字符，不截断源文本；角色和时间前缀随证据返回，前缀明确时间参照属于来源消息／会话，缺失时注明未知。来源标识与分块位置另存 metadata；内部 `source_time_kind = "message_or_session"` 不推断官方未提供的时间精度。

时间字段的定义、当前映射与目标策略见“时间语义与处理决策”。

成功响应：

```json
{
  "success": true,
  "request_id": "eval:run-1:locomo:conv-0:chunk-0",
  "user_id": "eval:run-1:locomo:conv-0",
  "session_id": "eval:run-1:session-0"
}
```

成功返回前完成 embedding（如已配置）和 MatrixOne 事务提交，记忆与请求凭据原子写入。相同 `user_id`、`session_id`、`request_id` 和语义请求内容重复提交不会重复写入；同一组合更换内容返回 409。幂等状态持久化在 `mem_source_requests`，进程重启和多实例重试均使用数据库记录。事务冲突等临时数据库错误返回可重试 5xx，不返回虚假的成功。

来源写入复用 Memoria embedding、实体索引及存储，作为 episodic 记录保存；不同来源事件不走原有事实注入的语义去重/覆盖流程。现有敏感信息策略仍生效：凭据等 HIGH 内容返回 403，邮件、电话等 MEDIUM 内容按 Memoria 原有规则脱敏后持久化、索引与返回。

## Search

```json
{
  "query": "What color was the telescope at Cedar Observatory?",
  "user_id": "eval:run-1:locomo:conv-0",
  "top_k": 100,
  "options": ["violet", "orange"]
}
```

`query`、`user_id`、`top_k` 必填；`options` 可选，接受但不拼入检索问题。当前服务支持 `top_k` 1—1000，AML 正式评测使用 100。Search 复用 Memoria 的 `retrieve_with_options_on_branch`，包含现有向量/全文检索及评分行为；不生成答案，不改变查询。

返回 `{"data": [...]}`，条目包含 `id`、`content`，有值时包含 `score`、`created_at`。按 Memoria 检索顺序返回，数量不超过 `top_k`；无结果返回空数组。完整证据内容不做字符截断。

## 隔离与运行边界

外部 `user_id` 按完整原值做带命名空间的哈希，映射到 64 字符的 `aml_...` 内部用户范围。会话标识也做稳定映射，原始标识保留在 metadata。响应原样返回外部标识。多数据库部署使用 Memoria 的用户数据库路由；不同 AML `user_id` 不共享记忆。固定读写 `main`，不受普通客户端切换活动分支影响。轮换专用服务 Key 不改变已有样本的存储范围。

继承 Memoria 的 2 MiB HTTP 请求体上限；超量明确返回 413，不静默截断。部署时应向 AML 申报此容量限制并按目标并发进行容量测量。

评测数据的 30 天删除要求由部署方负责执行，当前模块没有自动过期删除任务。清理时必须同时删除对应用户范围的记忆、来源 metadata、实体/日志等派生数据和 `mem_source_requests`；多数据库部署需完整清理对应评测用户数据库及共享登记。现有 `/admin/users/:user_id` 只做软删除，不能单独满足物理删除要求。专用 Key 只能交给评测平台与必要操作人员。

#### 评测与优化的实施门槛

1. **具体缺陷确认**：人工核对固定失败题，区分输入／持久化、候选召回、排序／上下文、Answer 和金标歧义。代码不变量被违反时可修复，不要求先跑完全部基准；目前的历史来源衰减和分数串用修正有独立语义依据。
2. **代表性本地评测**：建立固定种子的 100—200 题开发评测，覆盖多个对话及四类题型，记录各类和各对话题量、分项结果；保留未参与调优的对话用于验证。该规模是控制成本的工程起点，不是保证统计可靠的最小样本数，也不能将诊断集均分称为全集分数。
3. **分离回答与检索因素**：配置真正的 Qwen3-14B refined judge，对已保存预测评分，无需重跑 Add/Search。对选定失败题可增加原始完整会话的 Answer 对照，固定回答模型和提示词、披露上下文预算，用于判断回答瓶颈；此对照不是记忆检索排名，不能使用 gold 答案或 gold evidence 作为正常输入。
4. **算法对照条件**：固定数据、模型、提示词、分段、Top K 和证据预算，一次改变一个因素；在固定失败集和保留对话上比较 Recall@5／20／100、全部必要证据覆盖、语义分数及请求时延。少量代表题重复生成用于观察回答波动；不要将同一对话内的问题强行视为独立样本做置信区间。
5. **竞争力结论**：算法定版后完成 10 个对话的 861 道文本题，披露过滤条件、失败题及分项指标。与其他产品比较时，应在本地统一配置复跑基线或获得完全一致的公开协议；是否达到 AML 比赛水平最终通过其固定官方流程确认。

当前已完成严格裁判接通、150 题跨对话开发基线及批次内来源补全的部署／实际读取／首轮质量对照。语义判对率 78.67%→84.67%，时间题 55.56%→48.15%，Search P95 511→835 ms；本地保留实验配置，尚未定版。实验依据多对话的相邻问答缺失证据，保持固定题集、模型与预算；20 题均分不作为更换测试集或重构核心的依据。

### 优化归因与泛化验收

**本阶段范围为 AML 文本记忆参评，通过 `/aml/add` 与 `/aml/search` 验收。** 通用来源设计用于避免对 LoCoMo 特化；本阶段建立 AML 能力场景集，不扩展为 Memoria 全产品评测或新增 SDK／MCP／observe_turn 测试项目。涉及共享组件的改动仍需确认兼容性。LoCoMo 提供开发诊断证据。 在同一开发集上反复选择窗口、排序和名额，可能适应该数据的对话风格、题型比例及本地 Answer／judge，形成局部最优。通用数据结构和没有题号分支只证明实现没有显式依赖题目，不证明参数或质量收益已经泛化。当前 84.67% 只支持本轮 LoCoMo 开发对照的结论。

| 问题／动作 | 当前归因 | 处理与验收依据 |
|---|---|---|
| 限定数据库表名被拒绝，邻接读取回退 | 已确认的实现错误，已修复；与问题内容无关 | 当前路由数据库的合法限定名可读，其他范围与非法标识符被拒绝；通过数据库边界检查验收，不以榜单提分定义正确性 |
| 命中问题，却缺少依赖前文的短回复 | 原始对话来源路径的通用能力缺口，已有四个案例证实 | 任意同来源、有可靠顺序的问答／代词承接都可能需要完整证据；不能据此认定原有事实注入或 observe_turn 违反契约 |
| 邻居前置导致原命中后移、补全挤占名额 | 新补全策略的通用质量风险；当前是设计权衡，不是已证明的原业务契约缺陷 | 锚点保位、窗口内顺序和相关性过滤分别对照；同时检查完整证据、前位有效证据、话题干扰与预算，不能只看 Recall@100 |
| 半径 2、锚点 5、上下文 20 | 首轮开发实验参数 | 需跨场景验证；不能作为所有来源、问题、语言、Top K 和模型的默认最优值 |
| 日期证据已返回，回答仍为相对时间／不知道 | 完整检索—回答流程的失败，责任尚需区分；部分还有裁判争议 | 分别核查服务返回的来源时间／正文、证据次序、本地 Answer 推理及 judge；不因一次时间题降分就修改 Memoria 时间语义或衰减策略 |
| Search 时延增加 | 已观测性能代价，尚未完成阶段归因 | 分别测量基础召回、邻接读取与合成；控制输入和运行环境后判断，不把外部 embedding 或模型波动全部归于补全 |

**通用验收分两类**：用户／分支／来源批次隔离、active 与过滤条件、幂等、来源保真、Top K／字符预算以及分数含义属于明确约束，不能为得分突破。相关性、来源窗口顺序、锚点名次和补全名额属于质量策略；原检索排名也是近似判断，严格保持原名次并不天然最优，应由多场景证据选择。

本阶段评测按 AML Add/Search 路径分层。基础合成小集已生成并通过真实接口运行，入口为仓库内的 `scripts/aml_minimal_test.py`，使同事可直接复跑；跨场景难例、回答验收及独立保留集仍待扩展。该脚本使用相同 AML 请求字段，无需安装外部本地客户端：

1. **AML 能力场景开发集**：独立于 LoCoMo 原题建立约 40—60 道可核对的问题，全部以合法 AML 请求输入来源，覆盖事实、多跳、时间、偏好／规则、信息更新与干扰，并加入问答承接、话题突变、多人同类事件及长文本。包含补全有益、有害及无需补全三类；安排 Add→Search→Add→Search 的持续增量写入。默认对照 Top K 100，额外边界用例明确标记。数量是降低开发成本的工程目标，不是官方套件或统计门槛；能力标签需核对官方当期维度，不能将自建题目声称为官方样例。

4. **未用于调优的验收**：当前 50 题只提供同一数据集内的未见对话检验，不证明跨数据分布、语言或任务的泛化。策略确定后再运行；更广泛收益还需未参与开发的业务来源／任务，并采用一致的模型、提示词及预算。若根据验收结果继续调参，该集合应视为已用于开发，并保留新的未见验收材料。

200 题是降低调优成本的工程目标，不保证统计显著性。抽样时以实际可用题数为约束，开发集覆盖四类任务，不按源文件的前 N 题取样；开发与验证题清单在调优前冻结。已有 `conv-26` 小集已用于分析，不能再作为未见验证对话。分项均值、开发／验证均值和全集均值分别标明，不能将人为均衡的抽样总分当作原始分布总分。

算法选择由失败归因驱动：优先核查候选过滤与召回、证据正文结构和邻近消息关联，再决定是否对照 RRF 或 rerank。同事的 SQLite 参考实现可作为本地算法对照来源，比较时必须使用相同来源输入、问题、Answer 和 judge；正式部署继续只使用 Memoria。CJK 查询扩展需要独立中文质量集验收，英文 LoCoMo 不能证明其收益。若失败集中在 Answer，相应调整属于本地回答实验，不能当作 Memoria 检索提分或推断 AML 官方收益。

当前首要动作是扩展已完成的 AML 基础小集并补充回答／难例验收，然后以已完成的 ±2／5 锚点／20 上下文作为实验版本，先单独对照输出排序；固定 LoCoMo 150 题、模型、提示词和 Top K，同时检查 AML 场景。较小补全预算单独安排下一轮；每轮只改变一个因素。重点复核 conv-50 的日期／城市证据后移及相对时间回答，裁判争议单列，不改写标准分数。同时测量基础召回、邻接读取与合成阶段，评估时延代价；暂不引入新的 rerank 模型、RRF 或 CJK 扩展。跨批次补全需可靠来源顺序依据。完成开发对照与版本定版后运行 50 题保留验证，再安排全集与正式参评准备。

## 已知质量边界

在本地 MatrixOne 4.2.1、未配置 embedding 的验证中，原文“王强养了一只猫叫豆豆，今年三岁，住在杭州西湖区。”对连续自然问句“豆豆猫几岁了”未召回。接口测试使用明确词项“豆豆”验证中文文本运输、存储和检索。现有 ngram 全文检索不能据此视为等同于同事的 CJK 双字查询扩展；自然问句的召回应进入后续本地质量评测，结合实际 embedding 配置评估。

## 优化方案与实施顺序

以下按依赖关系实施；源码完成不等于已部署或已确认质量收益。所有质量收益需通过同配置的本地对照评测确认。

| 顺序 | 工作 | 决策及验收重点 | 状态 |
|---|---|---|---|
| 1 | 修正混合检索分数来源 | 合并前分别保存向量和全文分数；仅全文命中的候选向量分数为零；缺失分数不借用另一检索通道 | 已实现并完成小集组合对照；独立回归及单项收益尚未确认 |
| 2 | 来源证据生命周期 | 通用来源标记、无年龄衰减／接收时间加分、各来源检索路径及内置治理策略；明确删除和保留期限独立处理 | 年龄及内置治理策略已实现；保留期限清理待完成 |
| 3 | 时间上下文与检索 | 来源时间标签、会话级精度及 UTC 假设、消息／分块关联；进一步按问题语义加入时间信号与相邻上下文 | 时间说明和批次内补全已实现并部署；问题时间排序和跨批次补全待完成 |
| 4 | 事件时间与状态有效期 | 结合正文及来源时间提取事件时间与状态变更，保存推断依据和不确定性，并始终可追溯原始证据 | 待实现 |
| 5 | 检索算法对照 | 比较现有加权融合与 RRF、邻块补全、CJK 查询扩展等方案；根据固定失败集选择 | 批次内邻接首轮已完成；锚点保位、窗口／预算、RRF 与 CJK 对照待完成 |

混合检索、图候选选择、图结果及服务合并排序已添加稳定 ID 的同分排序规则，降低无序集合遍历导致的结果抖动。该规则只解决相同候选集合的同分排序，不保证近似向量召回或后台图构建结果完全确定。

新增本地时间能力评测应覆盖：绝对日期、相对日期、历史状态、明确的新旧状态更新、同一会话时间下的顺序、缺失时间、消息时间与事件时间不同、同一数据在不同导入时间下的稳定性，以及来源策略在全文／混合／图检索和治理中的一致性。评测设计不能将标准答案或金标 evidence 注入 Add、Search 或 Answer。

采用新的 run/user 范围对照检索变化，固定数据选择、模型、提示词和 Top K，分别记录证据召回、Token F1／BLEU-1、严格 judge（配置后）与时延。两项词面指标均为 0—1，越大越好，但不能等同于答案正确率。现有公共小集用于调优，七能力本地评测集仍需另行补齐。

## 正式参评准备

- 补齐评测范围完整物理清理，覆盖记忆、来源 metadata、实体／派生数据、幂等凭据和实际保存的日志／备份。
- 核对参赛组别的模型规则。当前本地 embedding 为 Shanghai BAAI/bge-m3（1024 维），内部 LLM 和本地 Answer 为 qwen-plus；开发配置不代表已满足正式规则，开源方法 Add 的模型使用范围需核对。
- 固定版本，准备公网 HTTPS、专用认证、明确的容量及并发说明，再完成官方 Smoke。通过本地验证不能替代官方验收。
- 检查后台实体任务可靠性。当前 Add 成功保证来源文本和配置的向量已提交，不保证整张实体图已构建；实体任务可能因队列满而丢失。图能力优化需明确可检索就绪范围及失败恢复方式。
